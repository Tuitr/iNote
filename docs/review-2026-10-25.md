# Код-ревью и готовность к проду — 25.10.2026

Ветка `zone-c` (Brain на GigaChat + подключение к агенту) и путь в прод для всего проекта.
Что проверено: весь код `libs/brain` построчно, его подключение в агенте и стенд; сверка клиента GigaChat
с официальной OpenAPI-спецификацией Сбера (`developers.sber.ru/docs/files/openapi/gigachat/api.yml`);
прод-обвязка (compose, Caddy, бот в режиме `real`, авторизация mini app, секреты). Остальной код зон C и D
повторно построчно не перечитывал — его разбирал пост-мерж ревью; линтеры, mypy, import-linter и 1239 тестов
зелёные.

## 1. Ошибки — чинить до подключения ключа

### 1.1 Результат инструмента уходит в GigaChat не в том формате (критично, мой код)
`gigachat.py` → `_message`, `llm_brain.py` → `_forModel`. Спецификация: сообщение `role: function` —
«результат работы функции в виде обернутого в строку JSON-объекта». Мы шлём строку `summary` как есть
(«Создано: [7f3a9c2e] …»). Ожидаемо GigaChat ответит 4xx → `llm_bad_output`.
Последствие хуже, чем просто ошибка: инструмент к этому моменту уже выполнен. «Напомни завтра в 10…» —
напоминание создано, а пользователь видит «что-то пошло не так» и повторяет — дубль.
Фикс: `content = json.dumps({"result": summary})` (ошибки уже JSON) и `functions_state_id` из ответа
модели передавать обратно в сообщении `assistant` — спецификация говорит, что это повышает качество.

### 1.2 Сбой LLM после успешного изменения превращает ход в ошибку (мой код)
`llm_brain.py` → `run`: `LlmError` на втором вызове модели → `outcome=error`, хотя `actions` уже содержит
успешный `create_task`. Фикс: если есть успешное изменение — `done` (подтверждение агент строит из data,
текст модели не нужен).

### 1.3 Бюджет времени хода не сходится (мой код)
Агент ждёт ход 40 с (`AGENT_TURN_TIMEOUT_S`). Один шаг модели в худшем случае: 20 с + пауза 1 с + повтор 20 с
+ запасная модель 20 с = 61 с; шагов до 4. Первый же медленный ответ GigaChat — `turn_timeout`, причём
возможно после уже выполненного инструмента. Фикс: дедлайн хода внутри `LlmBrain` (например, 35 с):
повтор и запасную модель пробовать, только если до дедлайна хватает времени; `LLM_TIMEOUT_S` по умолчанию 12.

### 1.4 «Готово» после поиска даёт `llm_no_action` (мой код)
`_final`: проверка «модель отчиталась без изменения» срабатывает и когда был поиск/список. Модель часто
пишет «Готово, вот что нашёл» → пользователь получает ошибку вместо результатов поиска. Фикс: проверять
только ход без вызовов (при чтении агент рисует данные, текст модели не показывается).

### 1.5 Мелочи Brain
- `check_conflicts.exclude_id` не проходит проверку «id только известный» (проверяется только `id`).
- Текстовый ответ на вопрос с кнопками (`pending: call`) модель понимает только по истории: аргументы
  прошлого хода (название встречи) ей не передаются. Стоит добавить в системный промпт строку
  «ждём ответ на вопрос …, известные аргументы …».
- Пересечение при переносе (`update_item`) уточняется окнами, но кнопки «Всё равно» у агента нет —
  только для `create_event` (`reply_renderer._forceButton`).

## 3. Чего не хватает для прода

### Блокеры
1. **Реального адаптера MAX нет.** `BOT_MAX_MODE=real` → `MaxAdapterNotChosenError` на старте, а
   `docker-compose.stand.yml` ставит именно `real`. Нужно: клиент MAX Bot API (отправка сообщений с
   inline-кнопками, ответ на callback, подписка webhook, long polling, скачивание аудио), переменная токена
   бота, `RedisMarkerStore` для polling. Решение «maxapi или своя обёртка» открыто — зона C.
2. **Mini app не собирается в стенд.** В compose `max_app` — заглушка E; у `max_app/` нет Dockerfile.
   Нужно: сборка статики (Vite) в образ, регистрация mini app в настройках бота MAX, проверка `start_param`.
3. **GigaChat:** фиксы 1.1–1.3, ключ в `.env`, сертификат НУЦ Минцифры смонтировать в контейнер агента
   (`LLM_GIGACHAT_CA_BUNDLE`) — сейчас в compose монтирования нет; первый `make eval`.
4. **Секреты перед выкаткой.** `stand-check.sh` проверяет только `SERVICE_TOKEN`, `BOT_WEBHOOK_SECRET`,
   домен и почту. Не проверяет: `POSTGRES_PASSWORD`, `API_JWT_SECRET`, `API_MAX_BOT_TOKEN` (в примере —
   `change-me…`), `API_DEV_AUTH=false`, ключи ASR и GigaChat для `full`.

### Нужно для нормальной эксплуатации
5. **Сервер и домен:** VPS с Docker, DNS на домен, открытые 80/443; `make deploy` собирает образы прямо
   на сервере. CD нет — выкатка руками.
6. **Бэкапы PostgreSQL:** данные только в volume `pgdata`, бэкапа нет. Минимум — ежедневный `pg_dump`
   по cron вне сервера.
7. **Наблюдаемость:** только логи контейнеров (`make logs TRACE=…`). Нет алертов на падение сервиса и на
   долю `llm_*`/`turn_timeout`.
8. **Стоимость LLM:** нет лимита ходов на пользователя — один активный пользователь может потратить бюджет
   GigaChat. Нужен дневной лимит в агенте.
9. **Проверка на живом MAX:** чек-лист из `deploy/README.md` (10 пунктов) — ни разу не пройден.
