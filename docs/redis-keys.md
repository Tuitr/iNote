# Реестр ключей Redis (J7)

Владелец — **C**. Новый ключ появляется только через PR сюда с ревью C (CODEOWNERS).
Ключ без строки в этой таблице в код не попадает; в тесте — проверка TTL.

## Правила

- Формат: `va:v1:<сервис>:<сущность>:<id>`. `<сервис>` и `<сущность>` — `[a-z][a-z0-9_]*`,
  `<id>` — `[A-Za-z0-9_.-]+`, **без `:`** (иначе ключ не разобрать). Строит ключи `common.redis.RedisKey`.
- **TTL у каждого ключа.** Единственное исключение — `va:v1:mcp:ver:{user_id}` (белый список
  `common.redis.NO_TTL_WHITELIST`); `KeyedRedis` откажется писать без TTL любой другой ключ.
- В Redis только то, что можно потерять: источник правды — PostgreSQL (правило 4 CLAUDE.md).
- Политика вытеснения — `volatile-lru`, `maxmemory` 256 МБ на стенде (`deploy/docker-compose.yml`):
  вытесняются только ключи с TTL, поэтому версии данных без TTL не пропадут, а кеш — может.
- `INCR va:v1:mcp:ver:{user_id}` — только после коммита в PG (правило 5).

| `va:v1:bot:rl:{max_user_id}` | бот | бот | 60 с | лимит 20 сообщений в минуту (INCR + EXPIRE NX), фиксированное окно | **в коде** |

## Проверки (S4)

- `tests/deploy/test_redis_registry.py` — реестр ↔ код: ключи, которые строит `RedisKey(...)` в боте и агенте,
  совпадают со строками зоны C (ни лишних, ни пропущенных), и каждый адаптер пишет ключ с TTL ровно как в таблице.
- `make redis-check` (`deploy/redis_check.py`) — на поднятом стенде: каждый ключ `va:v1:*` из реестра и с TTL > 0
  (без TTL — только `va:v1:mcp:ver:*`, его пишет D), `maxmemory` задан, политика `volatile-lru`. Запускается
  и после `make e2e`; то же — e2e-тест `tests/e2e/test_zz_redis_audit.py`.

## Память (замер S4, 23.10.2026)

`uv run python deploy/redis_load.py --users 200 --updates 20` на стенде `mock`: 200 пользователей, у каждого
18 фраз (каждая седьмая — голосом), 2 нажатия кнопок из ответов и одно уведомление J4. `MEMORY USAGE` ключей по
видам (Redis 7.4, значения — с накладными расходами ключа):

| Вид | Ключей за прогон | Байт за прогон | Байт на активного пользователя | Живёт |
|---|---|---|---|---|
| `bot:cb` | 7800 | 1 675 200 | 8376 | 24 ч — ~2 кнопки на ответ, ~215 байт на кнопку |
| `agent:ctx` | 200 | 524 800 | 2624 | 2 ч — 10 реплик |
| `bot:upd` | 4000 | 384 000 | 1920 | 24 ч — 96 байт на апдейт |
| `agent:focus` | 200 | 57 600 | 288 | 2 ч |
| `agent:user` | 200 | 40 000 | 200 | 1 ч |
| `bot:notif` | 200 | 24 000 | 120 | 24 ч |
| `bot:rl` | 195 | 14 040 | 70 | 60 с |
| `agent:pending`, `agent:lock`, `bot:notif_lock` | — | — | — | секунды–минуты, к концу прогона истекли |
| **всего по `INFO used_memory`** | | 4 128 096 | **≈ 20 КБ** | |

Вывод: при 20 сообщениях в день на пользователя 256 МБ хватает на **≈ 12 000 активных пользователей в сутки**
(основной объём — кнопки и дедуп, живут 24 ч). Для стенда и демо запас на два-три порядка. При росте первым
сокращать TTL `bot:cb` (кнопки старше суток всё равно редко нажимают); при переполнении `volatile-lru` вытеснит
ключи с TTL — худшее последствие: «Кнопка устарела» или повторная обработка апдейта, данные в PG не страдают.

## Как добавить ключ

1. Строка в таблицу выше: ключ, кто пишет и читает, TTL, зачем.
2. В коде — только через `RedisKey(service, entity, id)` и `KeyedRedis` с `ttlS`.
3. Integration-тест на настоящем Redis проверяет формат и TTL (пример — `services/bot/tests/integration/test_redis_adapters.py`).
