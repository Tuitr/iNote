# Команда и протоколы

Пятеро делят систему на пять зон и восемь стыков J1–J8. Каждый стык — договор двух людей: на встрече G1 его фиксируем кодом и моком, после этого все работают параллельно и не ждут друг друга.

## Кто за что отвечает

Пару ASR + LLM предлагаю разделить так: A — речь и эмбеддинги, B — промпт, цикл LLM и eval; набор фраз для проверки понимания они собирают вместе. Буквы A–E дальше обозначают участников; стыки J1–J8 описаны в разделах про контракты.

Цвет показывает владельца, пунктир — внешний сервис. Brain живёт внутри Agent Back, поэтому J2 — не сетевой вызов, а Python-интерфейс.

| Участник | Зона | Главный результат | Отдаёт другим | Ждёт от других |
| --- | --- | --- | --- | --- |
| A · речь | ASR-сервис, TTS (опция), эмбеддинги (предложение) | Голосовое из MAX превращается в текст для агента | J1 и фейковый режим ASR; `Embedder` для D; записи голосов для eval | Живые голосовые из MAX (C); размерность и место вызова эмбеддингов (D) |
| B · LLM | Brain внутри Agent Back: промпт, цикл инструментов, LLM-клиент; тексты описаний инструментов; eval | Фраза в свободной форме превращается в правильный вызов инструмента | J2 и `FakeToolExecutor`; тексты описаний инструментов для D | `ToolExecutor` и хранение уточнений (C); схемы и результаты инструментов (D) |
| C · бот и агент | Max bot, Agent Back (кроме Brain), Redis, `libs/common`, стенд | Сообщение в MAX — текст, голос или кнопка — получает ответ | Контракт ответа агента, приёмник J4, кнопки J6, реестр ключей J7, `libs/common`, стенд | J1 (A), Brain (B), MCP и служебный REST (D) |
| D · данные | PostgreSQL, migrate, `libs/core`, MCP, API, Scheduler | Данные сохраняются, находятся и напоминают о себе | J3, J5 (OpenAPI), J8, вызовы J4 | `Embedder` (A), описания инструментов (B), приёмник уведомлений (C) |
| E · фронт | MAX app | Календарь в MAX показывает то, что сохранил ассистент | Форматы `start_param` (J6) и требования к данным экранов | OpenAPI с примерами (D), кнопки мини-приложения (C) |

У D четыре контейнера — это самая большая нагрузка. Поэтому эмбеддинги уходят к A, а моки API E собирает сам по примерам из OpenAPI. `libs/common` нужна всем с первого дня, её делает C на этапе S0.

## Общие стандарты взаимодействия

Эти правила одинаковы для всех сервисов. Утверждаем их на встрече G0 и кладём в `docs/standards.md`.

**Транспорт**

- Сервисы говорят по HTTP/JSON внутри сети compose. Адреса — имена сервисов: `http://asr:8000`, `http://agent:8000`, `http://mcp:8000`, `http://api:8000`, `http://bot:8000`.
- Agent Back → MCP — протокол MCP поверх Streamable HTTP на `http://mcp:8000/mcp`. Служебный REST того же контейнера — `/internal/v1/*`.
- Наружу через reverse proxy с HTTPS открыты только `/webhook/max` (бот), `/api/v1/*` (API) и статика мини-приложения. MAX принимает webhook только по HTTPS на порту 443 с сертификатом от удостоверяющего центра.

**Авторизация и заголовки**

- Внутренние вызовы — `Authorization: Bearer <SERVICE_TOKEN>`, проверка — middleware из `libs/common`. Пути `/internal/*` наружу не публикуются.
- MAX app → API — JWT, который выдаёт `POST /v1/auth/max`.
- `X-Trace-Id` — на каждом внутреннем вызове. Создаёт тот, с кого начинается цепочка: бот (апдейт), Scheduler (уведомление) или API (запрос фронта). Формат — 32 hex-символа, пользователю в ошибках показываем первые 6.
- `Idempotency-Key` — на изменяющих вызовах между сервисами; для MCP — поле `caller.idempotency_key`.

**Данные**

- JSON в UTF-8, поля в `snake_case`, перечисления — строки в нижнем регистре: `kind` — `task` / `reminder` / `event`, `status` — `open` / `done` / `cancelled`.
- Время — ISO 8601 со смещением: `2026-10-18T10:00:00+03:00`. Время без смещения — ошибка `validation_error`. Дата без времени — `YYYY-MM-DD`, длительности — целые минуты в полях `*_min`.
- В БД время в UTC; наружу (MCP, API, уведомления) — в часовом поясе пользователя.
- Id записей — UUID строкой. Внутренний `user_id` не уходит ни во фронт, ни в LLM.
- Одна модель записи `Item` для всех (см. контракты ниже): MCP, API, уведомления и фронт рисуют одно и то же.
- Читатель игнорирует незнакомые поля. Добавить поле можно без встречи; удалить или переименовать — только через встречу по протоколам.

**Ошибки** — один конверт для всех HTTP-ответов:

```json
{"error": {"code": "not_found", "message": "Запись не найдена", "details": {"id": "7f3a9c2e-5b1d-4c8e-9a21-0d4e5f6a8b90"}, "trace_id": "ab12f0c4d5e6f708192a3b4c5d6e7f80"}}
```

| Код | HTTP | Когда |
| --- | --- | --- |
| `validation_error` | 400 | Неверные поля, время без смещения |
| `unauthorized` | 401 | Нет токена или он истёк |
| `forbidden` | 403 | Неверный сервисный токен |
| `not_found` | 404 | Записи нет или она чужая — ответ одинаковый, чтобы не раскрывать чужие id |
| `stale` | 409 | Запись изменилась после чтения (правка из MAX app) |
| `past_time` | 422 | Напоминание или встреча в прошлом |
| `rate_limited` | 429 | Превышен лимит запросов |
| `internal` | 500 | Непредвиденная ошибка |
| `upstream_unavailable` | 503 | Внешний сервис (LLM, ASR, MAX) недоступен |
| `upstream_timeout` | 504 | Внешний сервис не ответил вовремя |

Пересечение встреч — не ошибка, а обычный ответ со списком конфликтов.

**Время ответа**

- Бюджет голосового сообщения: ASR до 15 с, агент до 40 с (в худшем случае два вызова LLM по 20 с), бот ждёт агента до 45 с. Таймауты и повторы по сервисам — в главной вкладке.
- Повторяем только идемпотентные вызовы или вызовы с ключом идемпотентности.

**Redis, конфиг, логи, health**

- Ключи Redis — `va:v1:<сервис>:<сущность>:<id>`. У каждого ключа есть TTL, кроме версий данных `va:v1:mcp:ver:{user_id}`. Политика вытеснения — `volatile-lru`. Реестр ключей ведёт C (J7).
- Общие переменные окружения: `DATABASE_URL`, `REDIS_URL`, `SERVICE_TOKEN`, `LOG_LEVEL`, `LOG_FORMAT`, `DEFAULT_TZ`. Свои — с префиксом сервиса: `BOT_`, `AGENT_`, `ASR_`, `LLM_`, `MCP_`, `API_`, `SCHED_`. Новая переменная попадает в `.env.example` в том же PR.
- Логи — structlog с полями `service`, `trace_id`, `user_id`, `event`, `duration_ms`; токены и аудио не логируем.
- `GET /health/live` → 200; `GET /health/ready` → 200 или 503 со списком проверок: `{"status": "degraded", "checks": {"postgres": "ok", "redis": "fail"}}`.
- Версии: префикс `/v1`. Ломающее изменение — новое поле или эндпоинт, старое живёт до G4.

## Контракты J1–J4: что кто кому возвращает

Каждый стык описан кодом в `libs/contracts` и примерами в `contracts/examples/`. Владелец стыка отдаёт мок вместе с контрактом, чтобы вторая сторона не ждала реализации.

| Стык | Кто → кому | Протокол | Владелец контракта | Мок для старта | Фиксируем |
| --- | --- | --- | --- | --- | --- |
| J1 | Бот (C) → ASR (A) | HTTP `POST /v1/transcribe` | A | `ASR_MODE=fake` | G1; порог уверенности — G2 |
| J2 | Agent Back (C) ↔ Brain (B) | Python-интерфейс `Brain` | B вместе с C | `ScriptedBrain` у C, `FakeToolExecutor` у B | G1 |
| J3 | Agent Back (C) → MCP (D) | Инструменты MCP | D; тексты описаний — B | MCP-заглушка с готовыми ответами | G1; уточняем на G2 |
| J4 | Scheduler (D) → бот (C) | HTTP `POST /internal/v1/notify` | C | Пример запроса + curl-скрипт | Черновик — G1, финал — G3 |
| J5 | MAX app (E) → API (D) | REST `/v1` + JWT, OpenAPI | D | MSW по примерам из OpenAPI | G1; уточняем на G2–G3 |
| J6 | Бот (C) → MAX app (E) | `start_param` в кнопке мини-приложения или ссылке | E | — | Черновик — G1, финал — G3 |
| J7 | Все ↔ Redis | Реестр ключей | C | — | G0 |
| J8 | Agent Back (C) → MCP-контейнер (D) | Служебный REST `/internal/v1` | D | Заглушка на FastAPI | G1 |

### Модель записи Item — общая для J3, J4, J5

```json
{
  "id": "7f3a9c2e-5b1d-4c8e-9a21-0d4e5f6a8b90",
  "kind": "event",
  "title": "Встреча с Иваном",
  "notes": null,
  "starts_at": "2026-10-18T15:00:00+03:00",
  "ends_at": "2026-10-18T16:00:00+03:00",
  "all_day": false,
  "remind_at": "2026-10-18T14:45:00+03:00",
  "status": "open",
  "rrule": null,
  "participants": ["Иван"],
  "source_text": "Поставь встречу с Иваном завтра в три",
  "created_at": "2026-10-17T15:42:07+03:00",
  "updated_at": "2026-10-17T15:42:07+03:00"
}
```

Краткая форма `ItemBrief` — `id`, `kind`, `title`, `starts_at`, `all_day`, `status`: для фокуса диалога, конфликтов и истории.

### J1 · Бот → ASR

Запрос `POST /v1/transcribe`, `multipart/form-data`: `audio` — файл, `mime` — по умолчанию `audio/ogg`, `lang` — `ru-RU`. Ответ:

```json
{
  "text": "Напомни мне завтра в 10 утра позвонить Ивану",
  "raw_text": "напомни мне завтра в десять утра позвонить ивану",
  "confidence": 0.92,
  "low_confidence": false,
  "duration_ms": 3400,
  "provider": "salute",
  "cached": false
}
```

- Ошибки: `no_speech` (422) → бот отвечает «Не расслышал, повтори или напиши текстом»; `audio_too_long` (413); `unsupported_format` (400); `upstream_timeout` и `upstream_unavailable` → «Не получилось распознать, напиши текстом».
- Удобство для C и B: `text` уже с пунктуацией и цифрами — бот показывает его как есть, агент передаёт в LLM. `low_confidence` считает A: порог знает только он. Тексты для пользователя пишет C по коду ошибки.

### J2 · Agent Back ↔ Brain

```python
# libs/contracts/brain.py
class TurnInput(BaseModel):
    text: str  # что сказал пользователь
    input_type: Literal["voice", "text"]
    asr_low_confidence: bool = False
    now: datetime  # с часовым поясом пользователя
    tz: str  # "Europe/Moscow"
    history: list[Turn]  # последние 10 реплик
    focus: list[ItemBrief]  # записи, о которых шла речь
    pending: dict | None  # незавершённое уточнение, формат B
    settings: UserSettings


class ToolResult(BaseModel):
    ok: bool
    summary: str  # строка для LLM
    data: dict | None = None  # structuredContent из MCP
    error: ErrorInfo | None = None  # code, message, details


class ToolExecutor(Protocol):  # реализует C
    async def list_tools(self) -> list[ToolSpec]: ...  # уже без caller
    async def call(self, name: str, args: dict) -> ToolResult: ...


class Clarify(BaseModel):
    missing: list[str]  # ["starts_at"]
    options: list[str]  # ["10:00", "15:00"] — готовые кнопки
    pending: dict  # C хранит как есть


class TurnResult(BaseModel):
    outcome: Literal["done", "clarify", "answer", "error"]
    actions: list[ExecutedAction]  # name, args, ToolResult
    say: str | None  # вопрос или свободный ответ модели
    clarify: Clarify | None
    focus: list[str]  # id записей в фокусе после хода
    error_code: str | None  # llm_timeout, llm_rate_limited, llm_bad_output, llm_no_action
    usage: Usage  # model, llm_calls, tokens_in, tokens_out, latency_ms


class Brain(Protocol):  # реализует B
    async def run(self, turn: TurnInput, tools: ToolExecutor) -> TurnResult: ...
    async def resume(self, turn: TurnInput, choice: str, tools: ToolExecutor) -> TurnResult: ...
```

- Brain не видит `user_id` и не ходит в Redis и MCP сам — только через `ToolExecutor`.
- `pending` — непрозрачный JSON: C хранит его в Redis и возвращает в следующем `TurnInput`, не разбирая. Формат меняет B, не спрашивая C.
- По кнопке с вариантом C вызывает `resume`: Brain достраивает действие без вызова LLM.
- При `outcome = "done"` в `actions` есть все успешные изменения: подтверждение C рисует из их `data`, а не из текста модели.
- Ошибки LLM не выбрасываются наружу: `outcome = "error"` и `error_code`, по нему C выбирает текст ответа.

### J3 · Agent Back → MCP

Список инструментов и аргументов — в главной вкладке. У каждого инструмента есть служебный аргумент `caller`. Агент убирает его из схемы для LLM и всегда заполняет сам, даже если модель что-то туда положила:

```json
"caller": {"user_id": 17, "tz": "Europe/Moscow", "trace_id": "ab12f0c4d5e6f708192a3b4c5d6e7f80", "idempotency_key": "ab12f0c4d5e6f708192a3b4c5d6e7f80:1"}
```

Ответ инструмента состоит из двух частей: `content[0].text` — короткая строка для модели, `structuredContent` — полный JSON для агента. Пример — встреча пересекается с другой:

```
structuredContent:
{"status": "conflict", "item": null,
 "conflicts": [{"id": "b41c…", "kind": "event", "title": "Встреча с дизайнером", "starts_at": "2026-10-18T15:00:00+03:00", "all_day": false, "status": "open"}],
 "free_slots": [{"starts_at": "2026-10-18T16:00:00+03:00", "ends_at": "2026-10-18T17:00:00+03:00"}]}

content[0].text:
Не создано: пересекается с «Встреча с дизайнером» 15:00–16:00. Свободно: 16:00–17:00.
```

- Изменяющие инструменты возвращают `{"status": "created" | "updated" | "completed" | "deleted" | "conflict", "item", "conflicts", "free_slots"}`.
- `list_items` → `{"items": [Item], "range": {"from", "to"}, "truncated": false}`; строка для модели — по строке на запись с коротким id, сгруппировано по дням, не больше 30 записей.
- `search_items` → `{"results": [{"item": Item, "score": 0.83}], "best_match_confident": true}`: порог «уверенного» совпадения считает D, агент и фронт его не подбирают.
- Ошибка — `isError: true` и `{"error": {"code": "past_time", "message": "Время уже прошло", "details": {...}}}`; модель видит строку «Ошибка past\_time: время уже прошло».
- `id` принимается полностью или первыми 8 символами, если они однозначны: модели реже ошибаются в коротком id.

### J4 · Scheduler → бот

Запрос `POST /internal/v1/notify`:

```json
{
  "notification_id": "5c1e7a90-3f2b-4d6c-8e1a-9b0c2d3e4f5a",
  "kind": "reminder",
  "user": {"max_user_id": 123456789, "max_chat_id": 987654321, "tz": "Europe/Moscow"},
  "item": {"id": "7f3a9c2e-5b1d-4c8e-9a21-0d4e5f6a8b90", "kind": "reminder", "title": "Позвонить Ивану", "starts_at": "2026-10-18T10:00:00+03:00", "...": "остальные поля Item"},
  "fire_at": "2026-10-18T10:00:00+03:00",
  "attempt": 1
}
```

| Ответ бота | Что делает Scheduler |
| --- | --- |
| 200 `{"delivered": true, "message_id": "…"}` | Статус `sent` |
| 200 `{"delivered": true, "duplicate": true}` | Статус `sent`: бот уже отправлял это уведомление |
| 404 `chat_not_found` | Статус `failed` без повторов: пользователь заблокировал бота |
| 429, 5xx, таймаут | Повтор с увеличивающейся задержкой, до 5 попыток |

Бот отсекает дубли по `notification_id` (ключ в Redis на 24 ч): повтор после таймаута не пришлёт напоминание дважды. Текст и кнопки уведомления строит бот; Scheduler формата MAX не знает.

## Контракты J5–J8

### J5 · MAX app → API

Главный документ — OpenAPI, который FastAPI генерирует сам; D коммитит его в `contracts/openapi/api.json` с примерами ответов. E генерирует из него типы TypeScript и моки.

Мини-приложение только читает (решение 2026-10-22): кроме входа, все методы — `GET`. Настройки меняются через бота (J8 `PATCH /internal/v1/users/{user_id}/settings`).

| Метод | Ответ | Правила |
| --- | --- | --- |
| `POST /v1/auth/max` | `token`, `expires_at`, `me`, `start_param` | Тело `{"init_data": "<строка WebApp.initData как есть>"}`; `auth_date` не старше 1 ч; токен живёт 1 ч |
| `GET /v1/me` | `name`, `settings` | Настройки: `tz`, `voice_replies`, `default_event_min`, `remind_before_min` |
| `GET /v1/items?from&to&kind&status&group=day` | `range`, `version`, `days[]` (или `items[]` без `group`) | `from` включительно, `to` не включительно, даты в поясе пользователя; пустые дни тоже возвращаются |
| `GET /v1/items/search?q&limit` | `results[]`, `best_match_confident` | Тот же поиск, что у MCP |
| `GET /v1/items/{id}` | `Item` | Чужая запись → `not_found` |
| `GET /v1/dialog?limit&before` | `turns[]`, `next_cursor` | У реплик ассистента есть `items` (`ItemBrief`) — ссылки на карточки |

Ответ на `GET /v1/items?from=2026-10-19&to=2026-10-26&group=day`:

```json
{
  "range": {"from": "2026-10-19", "to": "2026-10-26", "tz": "Europe/Moscow"},
  "version": 42,
  "days": [
    {"date": "2026-10-19", "label": "Пн, 19 октября", "items": [
      {"id": "b41c2d7e-0a1f-4e2b-8c3d-5e6f7a8b9c0d", "kind": "event", "title": "Встреча с дизайнером",
       "starts_at": "2026-10-19T11:00:00+03:00", "ends_at": "2026-10-19T12:00:00+03:00", "all_day": false, "status": "open"}
    ]},
    {"date": "2026-10-20", "label": "Вт, 20 октября", "items": []}
  ]
}
```

- В примере запись сокращена; в жизни там полный `Item`. Внутри дня — сначала записи на весь день, потом по времени начала.
- Удобство для E: границы дней в поясе и подписи дней считает API — фронт просто рисует список.
- `ETag` в ответе равен версии данных пользователя. Запрос с `If-None-Match: "42"` без изменений возвращает 304 без тела: фронт дёшево опрашивает раз в 20 с и видит задачи, созданные голосом.
- При 401 фронт молча переавторизуется с тем же `initData`.

### J6 · Бот → MAX app

Бот открывает нужный экран мини-приложения кнопкой `open_app` или ссылкой `https://max.ru/<имя_бота>?startapp=<payload>`. Фронт читает `WebApp.initDataUnsafe.start_param` для маршрута; API возвращает тот же параметр уже проверенным.

| `start_param` | Экран |
| --- | --- |
| `today` | Сегодня |
| `day_2026-10-18` | Один день |
| `week_2026-10-19` | Неделя с указанного понедельника |
| `item_7f3a9c2e-5b1d-4c8e-9a21-0d4e5f6a8b90` | Карточка записи |
| `dialog` | История диалога |

- Разрешены только латиница, цифры, `_` и `-`, до 512 символов — иначе MAX выбрасывает параметр. Неизвестный формат открывает «Сегодня».
- В строке клавиатуры — не больше 3 кнопок типа `open_app` или ссылок.
- Как передать payload именно в кнопке `open_app`, в справке по кнопкам не описано. C и E проверяют это в S0; запасной вариант — кнопка-ссылка с `startapp`.

### J8 · Служебный REST на MCP-контейнере

Агент не ходит в PostgreSQL, а пользователи и история диалога живут в базе D. Поэтому рядом с инструментами для LLM есть обычный REST для агента — так служебные методы не попадают в список инструментов модели.

| Метод | Тело | Ответ |
| --- | --- | --- |
| `POST /internal/v1/users/resolve` | `{"max_user_id": 123456789, "max_chat_id": 987654321, "name": "Степан"}` | `{"user_id": 17, "tz": "Europe/Moscow", "settings": {…}, "created": false}` |
| `PATCH /internal/v1/users/{user_id}/settings` | `{"tz": "Asia/Yekaterinburg", "voice_replies": true}` | `settings` |
| `POST /internal/v1/dialog-turns` | `{"user_id": 17, "trace_id": "…", "turns": [{"role": "user", "text": "…", "input_type": "voice"}, {"role": "assistant", "text": "…", "item_ids": ["7f3a…"]}], "latency_ms": 2930}` | 202; повтор с тем же `trace_id` не создаёт дубль |

## Как и где взаимодействуют участники

Участники пересекаются в четырёх местах: в репозитории (контракты и ревью), на стенде (интеграция), в канале `#contracts` (изменения стыков) и на коротких созвонах.

**Репозиторий**

- Монорепо, ветки `feat/<зона>-<что>`, PR в `main` с ревью хотя бы одного человека.
- `CODEOWNERS`: `libs/contracts/**` — владелец стыка и потребитель; `services/mcp/tools/**` — D и B; `libs/brain/**` — B; `docs/redis-keys.md` — C; `contracts/openapi/**` — D и E.
- Снапшот-тесты на схемы инструментов, OpenAPI и примеры: поменял контракт и не обновил пример — CI красный.

**Моки — чтобы не ждать друг друга**

| Кто отдаёт | Мок | Кому нужен |
| --- | --- | --- |
| A | `ASR_MODE=fake`: текст из заголовка `X-Fake-Text` или из словаря фикстур | C |
| B | `FakeToolExecutor` с данными в памяти | B (eval), C (тесты) |
| C | `ScriptedBrain` — правила вместо LLM: «напомни…» → `create_task` | C |
| C | Живые апдейты MAX как фикстуры: текст, голос, кнопка, старт бота | A, C |
| D | MCP-заглушка: инструменты отвечают примерами из `contracts/examples` | B, C |
| D | OpenAPI с примерами — из них E собирает MSW | E |
| D | Dev-авторизация `API_DEV_AUTH=true`, только локально | E |

Профили compose: `mock` поднимает всё на фейках без ключей, `full` — с реальными провайдерами.

**Стенд**

- Один сервер с доменом и HTTPS: на нём webhook бота, API и мини-приложение. Владелец — C, запасной — D.
- Деплой из `main` через GitHub Actions по кнопке или `make deploy`. Перед встречами G2–G4 стенд должен быть зелёным.
- Тестовые аккаунты MAX у всех пятерых: каждый проверяет свою часть через настоящего бота.

**Общение**

- Ежедневный созвон на 15 минут: что сделал, что блокирует, какие контракты меняются.
- Канал `#contracts`: любое изменение стыка — ссылка на PR и кого оно касается.
- Ломающее изменение — 15-минутный созвон владельца и потребителя до мержа.
- Решения — в `docs/decisions.md`: дата, что решили, почему. По одной строке на решение.

**Правило изменения контракта**

1. PR в `libs/contracts` и `contracts/examples` — без реализации.
2. Аппрув потребителя.
3. Владелец реализует так, чтобы старое поле жило до G4, или обе стороны мержат в один день.
4. Сообщение в `#contracts`.

**Задача готова**, когда: тесты зелёные, примеры контрактов обновлены, в логах есть `trace_id`, новые переменные добавлены в `.env.example`, в README своей зоны есть абзац про сделанное.

Этапы S0–S4 идут у всех пятерых параллельно, а между ними — пять встреч по протоколам G0–G4. Длительность этапов условная: даты поставим, когда станет известен дедлайн.

Каждый ромб — встреча по протоколам; что на ней согласуем и что получим на выходе — в таблице ниже.

| Встреча | Когда и сколько | Кто | Что согласуем | Результат |
| --- | --- | --- | --- | --- |
| G0 · стандарты | До первой строки кода, 1 ч | Все | Общие стандарты из этой вкладки, структура репозитория, CODEOWNERS, ключи доступа, кто держит стенд, реестр ключей Redis | `docs/standards.md`, скелет репозитория |
| G1 · контракты v0 | Конец S0, 1,5–2 ч | Все, затем парами у каждого стыка | J1–J8 v0: модели, примеры JSON, моки; список инструментов и аргументов; `Item`; коды ошибок; правила толкования времени; `EMBED_DIM`; форматы `start_param`; что делать с напоминанием в прошлом | `libs/contracts` v0 в `main`, моки поднимаются в профиле `mock` |
| G2 · текстовый срез | Текст проходит бот → агент → MCP → PG на стенде, 1 ч | B, C, D; A и E слушают | Чего не хватает модели в строках `summary`; понятны ли ошибки инструментов; формат `pending`; отрисовка списков и поиска; порог `low_confidence` и лимит длины голосовых | Контракты v1, обновлённые описания инструментов |
| G3 · ТЗ на стенде | Обязательный результат ТЗ работает голосом на стенде, 1 ч | Все | J4 (уведомления), каталог кнопок и действий, J6 (ссылки в приложение), запись из MAX app — да или нет, формат истории диалога, ETag | Контракты v2, решение по записи из приложения |
| G4 · заморозка | Перед стабилизацией, 30 мин | Все | Больше никаких ломающих изменений; демо-сценарий; кто пишет какие разделы README | Тег `contracts-freeze`, сценарий демо |

**Внеплановое обсуждение нужно, если:**

- меняется или удаляется поле в любом стыке J1–J8;
- точность eval упала больше чем на 5 процентных пунктов после изменения промпта, описаний инструментов или модели;
- нужен новый ключ Redis или переменная окружения, которую читает чужой сервис;
- после G2 меняется схема БД так, что трогает API или MCP.

## Особо опасные места

Первые два риска блокируют всю команду, их закрываем в первый же день. Остальные проверяем на встречах из последнего столбца. Опасные места внутри одной зоны — во вкладках участников.

| Место | Чем опасно | Кто | Как защищаемся | Проверяем на |
| --- | --- | --- | --- | --- |
| Доступ к платформе MAX | Ботов и мини-приложения подключают только юрлица, ИП и самозанятые — резиденты РФ; токен выдают после модерации. Без токена нет ни бота, ни приложения | C, E | В первый день выяснить у организаторов, чей аккаунт используем; до тех пор — тестовый бот и фронт в браузере с фейковым `initData` | G0 |
| Голосовые из MAX | Формат вложения описан только сторонними разработчиками: `type: "audio"`, подписанная ссылка живёт около суток, контейнер OGG | C, A | В S0 поймать живой апдейт и сохранить как фикстуру; формат определять по байтам; скачивать сразу | G1 |
| Время и часовые пояса | Ошибка на час или на день незаметна в демо, но ломает напоминания | B, D, E | ISO со смещением везде; общая таблица толкования фраз; замороженное время в тестах; eval на граничные случаи | G1, G2 |
| Чужие данные | Если `user_id` придёт из ответа модели или запроса фронта без проверки, пользователь увидит чужие записи | C, D | `caller` всегда заполняет агент; репозиторий нельзя вызвать без `user_id`; подпись `initData` проверяется на сервере; тест «чужой id → not\_found» | G1, G3 |
| Тихие изменения инструментов | Поменяли имя аргумента или описание — агент падает или модель начинает ошибаться | D, B, C | Снапшот схем, CODEOWNERS, прогон eval перед мержем | G1–G4 |
| Дубли | Повтор апдейта, ретрай после таймаута или двойной клик создают две задачи или два напоминания | C, D | Дедуп апдейтов и уведомлений; `idempotency_key` + уникальный индекс; идемпотентные действия кнопок | G2 |
| Цепочка таймаутов | Голос → ASR → два вызова LLM → MCP легко выходит за 30 секунд | A, B, C | Бюджет времени по звеньям; ответ на webhook сразу; «печатает…»; понятный ответ при таймауте | G2 |
| Модель «сделала» без вызова | Пользователь видит «записал», а в базе пусто | B, C | Подтверждение только из `actions`; проверка «текст успеха без изменяющего вызова»; кейсы в eval | G2 |
| Кеш расходится с базой | Версию увеличили до коммита или Redis её вытеснил — фронт показывает старые данные | D, C | INCR после коммита; `volatile-lru`; TTL на кеш списков | G3 |
| Размерность эмбеддингов | Записана в миграции: смена модели ломает поиск | A, D | `EMBED_DIM` на G1; смена модели = миграция + переиндексация | G1 |
| Внешние API на демо | Лимиты или падение LLM и ASR ровно во время показа | A, B | Кеши, повторы с паузой, запасная модель или провайдер, записанное демо-видео | G4 |
| Секреты в репозитории | Токен бота или ключ LLM остаётся в истории git | Все | `.env` в `.gitignore`, проверка секретов в CI | G0 |
| Подпись `initData` | Пересборка строки ломает подпись; старый `auth_date` даёт войти по чужой ссылке | E, D | Отправлять строку как есть; `auth_date` не старше часа | G3 |
| Миграции после G2 | Переименованная колонка ломает API и фронт | D | После G2 — только добавляющие миграции | G2 |
| Перегрузка D | Четыре контейнера у одного человека — узкое место всей команды | D, все | Сначала обязательное ТЗ; эмбеддинги и eval поиска — у A; моки API — у E | G1, G2 |
