# D · MCP, БД, API, Scheduler

D отвечает за данные: всё, что ассистент сохраняет, находит и о чём напоминает. Зона — PostgreSQL, миграции, libs/core, MCP, API для мини-приложения и Scheduler.

## Зона и методы

**PostgreSQL и migrate.** Единственный источник правды. Схема — в главной вкладке; расширения `vector` и `pg_trgm`. Миграции Alembic накатывает одноразовый контейнер `migrate` до старта сервисов. В базу ходят только сервисы D.

**libs/core — общий слой для MCP, API и Scheduler.**

| Сервис | Что делает |
| --- | --- |
| `ItemService` | Создание, изменение, выполнение, удаление и восстановление; конфликты и свободные слоты; развёртка повторов; создание уведомлений |
| `SearchService` | Гибридный поиск: вектор, полнотекст и триграммы, слияние по рангу, порог «не найдено», `best_match_confident` |
| `TimeService` | UTC ↔ пояс пользователя; границы дня и недели в поясе пользователя |
| `UserService` | Поиск или создание пользователя по `max_user_id`, настройки |
| `Versioning` | INCR `va:v1:mcp:ver:{user_id}` после коммита |

Все методы репозиториев принимают `user_id` первым аргументом; метода «найти запись по id без пользователя» не существует.

**MCP (контейнер `mcp`).** Тонкий адаптер над core: проверяет сервисный токен, валидирует аргументы, вызывает сервис и собирает ответ из двух частей — строки для модели и JSON для агента.

| Метод | Что делает |
| --- | --- |
| `create_task`, `create_event`, `list_items`, `search_items`, `update_item`, `complete_item`, `delete_item`, `check_conflicts` | Инструменты для LLM (J3); аргументы — в главной вкладке |
| `POST /internal/v1/users/resolve` | Найти или создать пользователя (J8) |
| `PATCH /internal/v1/users/{user_id}/settings` | Часовой пояс и настройки |
| `POST /internal/v1/dialog-turns` | Записать ход диалога |

**API (контейнер `api`).** REST для MAX app: авторизация по подписи `initData` → JWT, списки по дням, поиск, карточка, история диалога, настройки; изменение записей — если решим на G3. ETag по версии данных пользователя. OpenAPI — главный контракт для E (J5).

**Scheduler (контейнер `scheduler`).** Цикл раз в 15 с:

| Шаг | Что делает |
| --- | --- |
| `claim_due` | Забирает до 50 созревших уведомлений: `FOR UPDATE SKIP LOCKED`, статус `sending`, аренда на 60 с |
| `deliver` | `POST bot/internal/v1/notify`; результат — по таблице ответов J4 |
| `reclaim_expired` | Возвращает в `pending` уведомления с истёкшей арендой |
| `schedule_next` | Для записей с `rrule` создаёт следующее уведомление |

## Стек и критерий готовности

- Python 3.12, FastAPI, uvicorn, pydantic v2.
- PostgreSQL 16 с pgvector (образ `pgvector/pgvector:pg16`), SQLAlchemy 2 (async) + asyncpg, Alembic, пакет `pgvector` для типа vector.
- MCP-сервер: официальный Python SDK `mcp` (FastMCP), транспорт Streamable HTTP; монтируется в FastAPI-приложение рядом с `/internal/v1`.
- python-dateutil (`rrule`), PyJWT, redis-py.
- Тесты: pytest, testcontainers (Postgres с pgvector, Redis), syrupy (снапшоты схем инструментов и OpenAPI), schemathesis (опция: прогон API по OpenAPI).

**Готово, когда:** все 8 инструментов работают; API соответствует OpenAPI; Scheduler на двух репликах не шлёт дублей; миграции поднимают базу с нуля одной командой; покрытие `libs/core` не меньше 80%.

Что отдавать, чтобы другим было удобно:

- Одна модель `Item` везде: в `data` инструментов, в API и в уведомлениях — у бота, агента и фронта один рендер.
- Время сразу в поясе пользователя: потребителям не нужно знать про UTC.
- У каждого инструмента `summary` — короткие строки для модели с id, а `data` — полный JSON для агента.
- Конфликт — не ошибка: `status: "conflict"` + `conflicts` + `free_slots`, агент сразу строит кнопки.
- Поиск отдаёт `best_match_confident`: агент и фронт не подбирают порог сами.
- Для фронта `group=day` возвращает все дни периода, включая пустые, с готовыми подписями.
- `ETag` равен версии данных пользователя: фронт дёшево проверяет, изменилось ли что-то.
- Заглушки появляются раньше реализации: MCP-заглушка и OpenAPI с примерами — к G1.

Полные контракты J3, J4, J5 и J8 — во вкладке Команда и протоколы.

## Опасные места

- **Фильтр по `user_id`.** Один забытый `WHERE user_id` — и пользователь видит чужие записи. Репозиторий не даёт метода без `user_id`, чужая запись отвечает `not_found`, на каждый метод есть тест.
- **Время.** Храним UTC, отдаём в поясе пользователя; границы «сегодня» и «недели» считаем в поясе пользователя; время без смещения отклоняем.
- **Версия — только после коммита.** INCR `ver` до коммита → API успевает закешировать старые данные под новой версией, и фронт их больше не перечитает.
- **Мягкое удаление.** `deleted_at IS NULL` во всех выборках, включая поиск и Scheduler: удалённая задача не должна напоминать.
- **Идемпотентность.** Без уникального индекса по `user_id` и `idempotency_key` повтор после таймаута создаёт дубль.
- **Scheduler.** Решение «пора ли отправлять» принимать по `now()` базы, а не по часам контейнера. Напоминание, созданное с временем в прошлом, либо отправляется сразу, либо отклоняется ошибкой `past_time` — решить на G1.
- **Схемы инструментов и OpenAPI — общие контракты.** После G2 — только добавляющие изменения; снапшот-тесты ловят остальное.
- **Эмбеддинги.** Размерность записана в миграции. Если эмбеддер недоступен, запись всё равно сохраняется и находится по полнотексту, а вектор досчитывается позже.
- **Проверка `initData`.** Секретный ключ — HMAC-SHA256 с ключом `WebAppData` от токена бота; подпись считается от отсортированных пар без `hash`, соединённых переводом строки. `auth_date` проверять: документация MAX рекомендует срок около часа.
- **Перегрузка.** У D четыре контейнера. Порядок приоритетов: создание, список и поиск → API чтения → Scheduler → изменения → повторы. Эмбеддинги и eval поиска берёт A.
